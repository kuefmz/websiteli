# websiteli.ch

## 2026 Conversion Redesign Audit And Plan

### Current Architecture Audit

- **Framework and build:** Astro 5 static site, deployed from `dist/`, with `@astrojs/sitemap` and no server runtime.
- **Routing:** `/` is a noindex client redirect to `/en/`. Localized pages use `/[locale]/`, `/[locale]/[page]/`, `/[locale]/services/[service]/`, `/[locale]/industries/[industry]/`, `/[locale]/blog/[slug]/`, `/[locale]/partners/event-organizers/`, plus legacy redirect pages for old services/packages/demo namespaces.
- **Languages:** `en`, `de`, `hu`, `pl`, `es`, `fr`, `it`, `cz`, `sk`, `pt`, `da`, `nl`, `ja`.
- **Translation architecture:** core shared copy lives in `src/content/locales/*.json`; larger content systems live in TypeScript modules such as `src/content/partners.ts`, `src/content/demos/index.ts`, `src/content/services.ts`, `src/content/industries.ts`, and blog post modules.
- **SEO metadata:** `src/layouts/Layout.astro` renders title, meta description, robots, OpenGraph, Twitter cards, canonical URL, and JSON-LD. Page-specific metadata is generated in route files and content modules.
- **Canonical and hreflang:** canonical URLs normalize to `https://websiteli.ch` with trailing slashes. `getAlternates()` and blog/service/industry alternates output hreflang links for supported locales plus `x-default` where alternates exist.
- **Sitemap and robots:** sitemap is generated by Astro with filters that exclude top-level redirect pages, legacy package/service redirects, and demo/example redirect namespaces. `public/robots.txt` allows crawling and references `https://websiteli.ch/sitemap-index.xml` and `/rss.xml`.
- **Structured data:** default Organization, WebSite, and ProfessionalService schema is emitted globally. Services, industries, partners, pricing FAQ, blog posts, breadcrumbs, FAQ, images, and some software pages add route-specific schema.
- **Analytics:** `Layout.astro` loads Contentsquare and GA4, centralizes `window.trackWebsiteliEvent`, and supports `data-track-event`. Pricing runtime tracks market detection, package views, and package CTA clicks.
- **Forms and endpoints:** `CTASection.astro` and newsletter forms post JSON to the same Google Apps Script endpoint with `mode: "no-cors"`, honeypot fields, privacy acceptance, attribution, UTM metadata, pricing metadata, success states, and GA events.
- **Contact form topic/request values:** the contact select is built from package keys: `digitalFoundation`, `growthSetup`, `aiDataUpgrade`, `websiteMaintenance`, `digitalAudit`, plus `custom`. Hidden metadata includes `packageKey`, `relatedDemo`, `relatedProject`, `sourcePage`, and `inquiryIntent`.
- **Navigation:** desktop nav currently shows Home, Services & Pricing, Portfolio, Partners, Blog, About, a demo CTA, quote/contact CTA, language switcher, and theme toggle. Mobile nav mirrors the important items and languages.
- **Homepage before redesign:** homepage leads with a multi-capability business-growth-engine hero, intro strip, trust badges, services/category cards, automation band, AI section, industry grid, technology grid, demos CTA, outreach block, and contact CTA.
- **Service pages:** generated from `src/content/services.ts`, preserving service slugs, Service schema, FAQ schema, breadcrumbs, related services, pricing CTA, and analytics.
- **Industry pages:** generated from `src/content/industries.ts`, preserving industry slugs, long-tail SEO content, related services, FAQ schema, breadcrumbs, and analytics.
- **Portfolio:** currently powered mostly by demo content in `src/content/demos/index.ts`, mixing live demo websites with concept demos and detailed technology/package metadata.
- **Partner pages:** `/[locale]/partners/` uses `PartnersPage.astro` and `src/content/partners.ts`; `/partners/event-organizers/` and localized event partner routes preserve dedicated wedding/event partner material.
- **Blog and RSS:** blog posts are TypeScript content modules with localized translations, Article schema, FAQ schema, breadcrumbs, featured images, CTAs, and `/rss.xml`.
- **Internal linking:** header, footer, homepage, service pages, industry pages, blog CTAs, partners, and portfolio all link into localized service, industry, pricing, portfolio, partners, blog, and contact routes.
- **Reusable components:** shared components include Header, Footer, Layout, CTASection, PackageCard, FAQ, ProcessStep, PartnersPage, EventOrganizerPartnersPage, PricingRuntime, AttributionRuntime, and article components.
- **Existing CTAs and popups:** primary contact form is reused through `CTASection.astro`. Footer includes newsletter popup infrastructure, and `ExitIntentFeedback.astro` provides the active privacy-aware website feedback popup.
- **Mobile navigation:** fixed header with menu toggle, hidden desktop nav below 780px, localized language links in mobile menu.
- **Image handling and performance:** static assets live in `public/assets` and `public/images`; images use explicit dimensions in most visible cards/articles; Astro static output keeps runtime JS limited to analytics, pricing, forms, menus, theme, and popups.

Astro website for **websiteli.ch**, a Swiss digital agency for AI-powered websites, business automation, AI integrations, internal tools, dashboards, and custom web applications.

The site builds as static Astro pages for GitHub Pages and is served from the custom domain `https://websiteli.ch`. Language routes and pricing are intentionally separate: `/en`, `/de`, `/hu`, `/pl`, `/es`, and `/fr` control copy, while the browser pricing runtime resolves the visitor's market/currency from their IP location.

## Requirements

- Node.js 20 or newer for local builds
- npm

This project currently uses Astro 5, which builds successfully with Node 20.

## Location-Based Pricing

Pricing is resolved in the browser from `src/config/pricing.json`.

Resolution order:

1. Deployment-provided country metadata if exposed to the page.
2. Browser-side IP country lookup services.
3. `DEFAULT` pricing, which currently uses EUR.

EU countries fall back to the `EU` pricing config unless a dedicated country config exists. Visitors cannot manually change currency; language route and pricing market remain separate.

## Inquiry Tracking

The contact form posts JSON to `PUBLIC_CONTACT_FORM_ENDPOINT` or `PUBLIC_LEAD_FORM_ENDPOINT`. This is expected to be the Google Apps Script / Google Sheets bridge; keep credentials and sheet access inside that backend, not in this repo.

New submissions include the original fields plus metadata columns/keys such as:

```text
packageKey, locale, country, pricingMarket, currency, priceShown,
sourcePath, currentUrl, referrer, utm_source, utm_medium, utm_campaign,
utm_term, utm_content, timestamp, userAgent
```

If the Google Sheet has fixed columns, add these columns there. Older submissions still work because the frontend still sends the previous core fields.

## Adding Services

Add a service entry in `src/content/services.ts`. Each service should include:

- slug, title, category, description
- problem and solution copy
- benefits and ideal clients
- technologies
- pricing guidance through a package key
- related services for internal links

The dynamic route automatically adds canonical metadata, hreflang alternates, Service schema, FAQ schema, breadcrumbs, CTAs, and analytics events.

## Adding Industries

Add an industry entry in `src/content/industries.ts`. Each industry should include:

- challenges
- website recommendations
- automation opportunities
- AI opportunities
- SEO strategy
- related service slugs
- one fictional or generic demo idea

Do not invent testimonials, reviews, performance metrics, or completed client projects.

## Automation Showcases

Homepage automation chips come from `automationShowcaseTasks` in `src/content/services.ts`. Use plain business-language task names such as invoice sending, PDF processing, CRM updates, report generation, or Google Workspace automation.

## Demo Gallery

Demo content lives in `src/content/demos/index.ts`.

- `demoSlugs` controls redirect-compatible published demo routes.
- The portfolio gallery shows generic or fictional concepts, plus public Websiteli-owned demos.
- Personalized prospect demos should not be exposed publicly.
- Add `websiteUrl` only when there is a real public demo to open.
- Do not label a concept as a completed client project unless it is real and approved for publication.

## Blog Posts

Blog posts live in `src/content/blog/posts/` and are registered in `src/content/blog/index.ts`.

Use one TypeScript file per post, with all locale translations inside the post file's `translations` object. Blog article pages automatically render metadata, article schema, FAQ schema, breadcrumbs, CTAs, sharing, related links, and newsletter conversion paths.

## SEO

The site uses:

- clean canonicals
- hreflang alternates
- generated sitemap
- OpenGraph and Twitter metadata
- Organization, WebSite, LocalBusiness, Service, FAQ, Breadcrumb, BlogPosting and SoftwareApplication schema where appropriate
- static Astro output for performance

Then inspect generated HTML under `dist/` for canonical, title, description, structured data and sitemap inclusion.

## Deployment

Build verification is configured through GitHub Actions in:

```text
.github/workflows/deploy.yml
```

This workflow verifies the static build and deploys it to GitHub Pages.

On every push to the `main` branch, GitHub Actions will:

1. Install dependencies.
2. Run the pricing tests.
3. Verify that the generated `dist/` output includes the expected files.
4. Upload and deploy the static site to GitHub Pages.

GitHub repository settings must use:

```text
Settings -> Pages -> Source: GitHub Actions
Custom domain: websiteli.ch
```

Keep `public/CNAME` set to `websiteli.ch` and keep Astro's `site` config set to `https://websiteli.ch`. Do not add an Astro `base` value while the site is served from the custom domain root.
